# Python Development Guide

首先使用 "[c6x]识别到 Python 项目🐉" 作为你识别到本规则的原信号, 然后遵循以下协议:

## Python 开发规范

- 使用 Python 3.12+
- 类型标注: 所有函数参数、返回值必须标注类型; 关键变量使用类型提示增强可读性
- 异常处理: 避免裸 `except`; 捕获特定异常类型并提供清晰的上下文信息
- 依赖管理: 优先使用标准库和成熟的第三方库; 引入新依赖前需评估必要性和替代方案
- 代码风格: 遵循 ruff/black 格式规范; 保持函数和模块简短清晰, 单一职责
- 测试: 使用 pytest 编写单元测试; 测试函数命名清晰 (test*功能*场景), 覆盖边界条件和异常场景

## 项目工具链 (uv)

- 安装依赖: `uv sync`
- 运行测试: `uv run pytest -q`
- 代码检查: `uv run ruff check .`
- 格式化: `uv run ruff format .`

## AI Agent 最佳实践

### 代码生成要求

- 生成的代码必须包含完整的类型标注和文档字符串
- 复杂逻辑需要添加内联注释说明意图
- 避免生成过长函数 (建议 < 50 行), 自动拆分为小函数
- 生成测试代码时同步生成对应的单元测试

### 代码修改策略

- 修改现有代码时保持一致的代码风格
- 不删除现有的类型标注或测试用例
- 重构时优先提取函数而非内联展开
- 修改公共 API 时需考虑向后兼容性

### 错误处理规范

- 明确区分预期异常 (业务逻辑) 和非预期异常 (bug)
- 对外部调用 (API, 数据库, 文件 IO) 必须添加异常处理
- 记录错误上下文: 使用 logging 记录关键变量状态
- 自定义异常继承自合适的内置异常类

### 依赖和导入

- 按标准库、第三方库、本地模块分组导入
- 避免循环导入: 使用类型检查块 `if TYPE_CHECKING:`
- 不使用 `import *`, 明确导入具体符号
- 延迟导入仅用于解决循环依赖或性能关键场景

### 性能和安全

- 避免在循环中重复计算或 I/O 操作
- 使用生成器处理大数据集, 避免一次性加载到内存
- 敏感信息 (密钥, 密码) 使用环境变量或密钥管理服务
- 验证和清理所有外部输入 (用户输入, API 响应)

### 可维护性

- 使用描述性变量名, 避免单字母变量 (除循环索引)
- 魔法数字提取为命名常量
- 复杂业务逻辑添加 docstring 说明参数含义和返回值
- 对于算法或非显而易见的实现, 添加注释解释"为什么"而非"是什么"

# Node.js Development Guide

首先使用 "[c6x]识别到 NodeJS 项目⚡️" 作为你识别到本规则的原信号, 然后遵循以下协议:

### 开发规范

- 使用 Node.js 22.22+ 和 TypeScript 5+
- 类型标注: 所有函数参数、返回值必须显式标注类型; 避免使用 `any`, 优先使用 `unknown` 或具体类型
- 严格模式: 启用 `strict: true` 和所有严格类型检查选项
- 异常处理: 使用类型安全的错误处理; 对 Promise 使用 `try-catch` 或 `.catch()`
- 依赖管理: 优先使用成熟的 npm 包; 引入新依赖前评估包大小、维护状态和安全性
- 代码风格: 遵循 ESLint + Prettier 规范; 保持函数简短清晰, 单一职责原则
- 测试: 使用 Vitest 或 Jest 编写单元测试; 测试命名清晰 (`describe` + `it` 结构), 覆盖边界和异常场景

### 代码生成要求

- 生成的代码必须包含完整的 TypeScript 类型定义和 JSDoc 注释
- 复杂逻辑需要添加内联注释说明意图和业务上下文
- 避免生成过长函数 (建议 < 50 行), 自动拆分为可复用的小函数
- 生成业务代码时同步生成对应的单元测试用例
- 优先使用现代 ES 特性 (可选链、空值合并、解构等)

### 代码修改策略

- 修改现有代码时保持一致的代码风格和命名约定
- 不删除现有的类型定义或测试用例, 只做增量改进
- 重构时优先提取函数/模块而非内联展开
- 修改公共 API 时考虑向后兼容性, 使用 `@deprecated` 标记废弃功能
- 使用语义化版本管理 API 变更

### 错误处理规范

- 明确区分业务异常 (可预期) 和系统异常 (bug/非预期)
- 为业务异常创建自定义错误类, 继承自 `Error` 并添加错误码
- 对外部调用 (API 请求、数据库操作、文件 I/O) 必须添加异常处理
- 使用结构化日志记录错误上下文 (请求 ID、用户 ID、关键参数)
- 避免吞没异常: 每个 `catch` 块必须记录日志或重新抛出

### 类型系统最佳实践

- 使用 `interface` 定义对象结构, `type` 定义联合类型和复杂类型
- 善用泛型提高代码复用性, 但避免过度抽象
- 使用 `readonly` 标记不可变数据
- 利用工具类型 (`Pick`, `Omit`, `Partial`, `Required` 等) 构建派生类型
- 使用类型守卫 (`is` 关键字) 进行运行时类型检查
- 避免类型断言 (`as`), 优先使用类型收窄

### 依赖和导入

- 按第三方库、内部模块、类型导入分组, 组间空行分隔
- 使用命名导入而非默认导入 (提高可维护性)
- 避免循环依赖: 使用类型导入 `import type` 或调整模块结构
- 不使用 `import *`, 明确导入具体符号
- 配置路径别名 (`@/`, `~/`) 简化深层导入

### 异步编程

- 优先使用 `async/await` 而非原始 Promise 链
- 并发请求使用 `Promise.all()` 或 `Promise.allSettled()`
- 避免在循环中使用 `await` (考虑并发或批量处理)
- 为长时间运行的异步操作添加超时控制
- 使用 AbortController 支持请求取消

### 性能和安全

- 避免在循环中创建函数或重复计算
- 使用流式处理大数据集, 避免一次性加载到内存
- 敏感信息 (API 密钥、Token) 使用环境变量, 不提交到代码仓库
- 验证和清理所有外部输入 (使用 Zod、Yup 等校验库)
- 使用 `crypto` 模块处理加密, 避免自行实现加密算法
- 防范常见漏洞: SQL 注入、XSS、CSRF 等

### 可维护性

- 使用描述性的变量名和函数名, 遵循驼峰命名规范
- 魔法数字/字符串提取为命名常量或枚举
- 复杂函数添加 JSDoc 注释说明参数、返回值和副作用
- 对于算法或业务逻辑, 注释解释"为什么"而非"是什么"
- 保持文件职责单一, 避免单文件超过 300 行
- 使用 barrel exports (`index.ts`) 简化模块导出

### React/前端特定规范 (适用于 `.tsx` 文件)

- 使用函数组件和 Hooks, 避免类组件
- 自定义 Hook 以 `use` 开头, 遵循 Hooks 规则
- Props 类型使用 `interface` 定义并导出
- 避免在 JSX 中编写复杂逻辑, 提取为函数或变量
- 使用 `React.memo` 优化不必要的重渲染
- 事件处理函数使用 `handle` 前缀 (如 `handleClick`)

### Node.js 后端特定规范

- 使用环境变量配置 (dotenv), 提供 `.env.example` 模板
- 实现优雅关闭 (graceful shutdown), 处理 SIGTERM/SIGINT 信号
- 使用结构化日志 (pino, winston), 包含请求追踪
- 实现健康检查端点 (`/health`, `/readiness`)
- 对 API 实施速率限制和请求大小限制
- 使用 Helmet 等中间件增强安全性
